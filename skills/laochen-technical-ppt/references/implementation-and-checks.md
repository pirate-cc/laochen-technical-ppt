# Implementation and optional checks

Read only the section needed for the current operation. Reuse the active presentation capability and the project's own tooling; these references do not authorize installing another library, changing the agreed format, or replacing the user's chosen application.

## When to use checks

Use the [task scope](../SKILL.md#task-scope) to distinguish authoring, read-only review, and review with authorized repairs. A review request permits the relevant inspection and a report of findings, evidence, and suggestions; it does not by itself authorize changing the deck. When repairs are also requested, fix the identified issues within that scope and repeat only the affected checks. Correcting errors introduced by the current authoring task is part of that task.

For ordinary authoring, refine the wording and title/body/image correspondence, implement the intended effects, complete the minimum production confirmation below, and deliver for the user to inspect. Finished-deck rendering, screenshots, application reopening/edit trials, playback, accessibility audits, rehearsal, and regression are additional checks performed only when the user requests the corresponding review. Review of one aspect does not automatically start every other check. Follow [skill integration](../SKILL.md#working-with-other-skills) when a general presentation workflow has broader defaults.

## Minimum production confirmation

Select the relevant checks from the actual edits and the resources rewritten by the tool. Use authoring results plus saved-object records or read-only package inspection as needed. Confirm the saved authoritative output, not just script completion or an in-memory plan. This does not require opening the application, rendering slides, or creating a separate report.

| Affected part | Confirm during production |
| --- | --- |
| Saved output and page structure | The requested file was saved successfully and the exporter or package reader reports no structural errors. Resolve the presentation's page list and relationships to check the agreed count/order and referenced parts; do not assume that counting files named slide*.xml gives the presentation order. |
| Native content and chart data | Requested text, tables, labels, units, and objects were written with the required editing granularity. When creating or changing a chart, keep series/categories, data references, cached values, and any embedded workbook consistent with the supplied data; preserve required formulas and source lineage. |
| Consumed assets and fonts | Newly used images/media and required source files resolve from their saved locations or are embedded as agreed. Confirm the fonts used by the authoring environment and retain known delivery dependencies; do not substitute a font or leave a temporary URL as the only asset source silently. |
| Animation | Reconcile planned stages with actual saved effects: targets exist, triggers/order match the explanation, required stages are present, and duplicates are intentional. New or wholly remade live decks include every slide; local edits cover the affected objects and their effect dependencies. A p:timing element or total effect count alone does not establish coverage or sequencing. |

Fix demonstrated production errors within the authorized scope. For a local edit, follow only the necessary dependencies, including shared resources if the tool rewrites them; these checks do not authorize unrelated content changes. If a required write cannot be confirmed, report the specific affected feature and retain usable work. Structural confirmation does not establish visual layout, playback, or cross-application behavior.

## Choose the working surface

- In ChatGPT for PowerPoint, work in the currently open presentation. Prefer duplicating a representative existing slide and replacing its content.
- In Codex or ChatGPT Work, use the available presentation capability to read the template and sources, create or edit the `.pptx`, and deliver it under the checks policy above.
- Use Template Creator only when the user wants the presentation format saved for reuse. A reusable template and this workflow skill serve different purposes: the template controls appearance; this skill controls the method.
- If no actual template or reference presentation is available, do not claim template fidelity. Ask for the file before making a final deck when fidelity is required.
- Choose an authoring tool that supports the required template import, original-object editing, chart data, and native animation. Establish these capabilities from the selected tool's current interfaces/documentation or relevant project experience before committing the production route. Creating a new master is not template import, and rebuilding an approximation is not editing the original objects. Reference libraries are not required installations or substitutes for the user's chosen tool. Report a concrete unsupported operation and continue independent work without silently reducing the agreed output.

Estimate live-talk timing from explanation complexity, builds, pauses, and transitions within the agreed time; do not distribute time evenly by slide count. Keep planned duration separate from measured rehearsal, rehearse only when requested, and preserve manual advance when the presenter controls pacing.

## Template and object editing

- Retain the template's master/layout relationships and the particular original objects in scope using the supported route selected above. Local edits follow the existing page and object structure rather than rebuilding the deck.
- Identify target objects by stable name, role, or object identity. Edit only the intended content. Preserve paragraph/run properties, indentation, bullets, links, emphasis, and useful theme inheritance. If a replacement rebuilds the whole text body, restore the formatting explicitly and confirm the saved writes.
- Define editability by the promised operation: change text, edit table cells, adjust technical labels/connectors, or edit chart data. Background photographs need not become vectors. Do not satisfy a required editable diagram with a screenshot; report unsupported operations and continue independent pages.
- Chart/data agreement is part of production when that chart is created or changed, as defined in [minimum production confirmation](#minimum-production-confirmation). A requested native-chart review may additionally inspect the saved deck in the application and exercise editing when that is in scope. A visible chart or an embedded workbook alone does not prove they agree. For a complex scientific plot supplied as a figure, retain the agreed data/plot source and state its actual editing boundary; never rasterize a required native object without the user's agreement.

Source examples inspected on 2026-10-15, not runtime certification: [PptxGenJS README](https://github.com/gitbrent/PptxGenJS/blob/3c9ec1b687c174952166f6a34b5e87ebf69fa469/README.md) documents generation and custom masters; [python-pptx TextFrame.text](https://github.com/scanny/python-pptx/blob/278b47b1dedd5b46ee84c286e77cdfb0bf4594be/src/pptx/text/text.py#L172-L178) clears and rebuilds paragraphs; [Chart.replace_data](https://github.com/scanny/python-pptx/blob/278b47b1dedd5b46ee84c286e77cdfb0bf4594be/src/pptx/chart/chart.py) updates both chart XML and the embedded workbook. These examples illustrate what to check, not a requirement to use those libraries.

For new pages, duplicate suitable representative template slides and retain the background, master, typography, footer, logo, and proportions. Arrange the needed content before reducing type size; choose another composition in the same visual language if needed. For a code explanation, show only the lines that explain the operation and keep their explanation nearby.

## Chinese text fitting and fonts

- Use the actual Chinese, Latin, and mathematical fonts, margins, spacing, and final box dimensions when checking fit. Inspect missing glyphs, unintended fallback, punctuation at line boundaries, subscripts/superscripts, symbols, and number/unit combinations. An English word-based estimator is provisional for Chinese text.
- Preserve the template's readable hierarchy. Resolve overflow through meaningful editing and layout within the approved count before reducing size. Do not impose a universal point size, line count, or character quota; inspect the agreed projection or reading context.
- When visual review is requested, render the saved deck, not merely an in-memory authoring canvas, and inspect affected text after object regrouping, font replacement, or conversion. Text fitting properties are not proof of final layout.
- Confirm target font availability for portable/offline use. Embed only when the application and font license permit it, balancing file size and intended editing. Embedding only used characters can limit later edits; embedding full characters may be useful when others must add text. Do not silently outline or rasterize text to conceal a missing font. If font replacement changes the confirmed style materially, propose that specific change.
- When PDF is an agreed deliverable, create it and apply the agreed inspection scope. It does not replace the editable deck or certify animation.

Version-specific examples: [PptxGenJS fit notes](https://github.com/gitbrent/PptxGenJS/blob/3c9ec1b687c174952166f6a34b5e87ebf69fa469/src/core-interfaces.ts#L1007-L1010) explain that shrink/resize behavior is triggered by editing text or resizing shapes; [python-pptx _LineSource](https://github.com/scanny/python-pptx/blob/278b47b1dedd5b46ee84c286e77cdfb0bf4594be/src/pptx/text/layout.py#L237-L248) splits candidate lines by whitespace-delimited words. Verify the selected tool/version rather than generalizing these limitations. [Microsoft font embedding guidance](https://support.microsoft.com/en-us/office/fonts/benefits-of-embedding-custom-fonts) covers character subsets, licensing, and editing implications.

## Scientific charts

- Choose the display from the question: comparison, trend, distribution, or relationship. Preserve actual values, comparison baselines, units, transformations, and time or event ordering. Avoid misleading axes, unsupported continuity, and decorative encodings that change interpretation.
- Use colors according to their meaning: categorical identities, ordered magnitude, deviations around a meaningful reference, or emphasis. Keep recurring identities consistent across slides. A theme palette must not erase a field convention or make ordered data appear categorical. Retain the colorbar/reference when needed.
- Use direct labels for a few series when space allows; keep a legend for dense or shared encodings. Place important conditions and annotations near the relevant evidence without masking it.
- State what uncertainty marks represent: SD, SE, a specified confidence/credible interval, or another source-defined quantity. Preserve sample size and repetition unit where they affect interpretation. Do not invent intervals or interchange their definitions.
- Select a paper figure with labels suitable for its intended slide size. During a requested visual review, inspect it at final projected size. If labels are unreadable, select and enlarge relevant panels, provide overview plus detail, or redraw using available source data. Retain necessary controls, axes, units, color scales, and qualifications. Never infer numerical data from a picture merely to make an editable chart.

References: [Wilke on color scales](https://clauswilke.com/dataviz/color-basics.html), [time-series labels](https://clauswilke.com/dataviz/time-series.html), and [uncertainty](https://clauswilke.com/dataviz/visualizing-uncertainty.html). [Nature figure guidance](https://research-figure-guide.nature.com/figures/building-and-exporting-figure-panels/) concerns publication figures; do not import its print-size typography as a slide font prescription.

## Accessibility

- During a requested accessibility review, inspect contrast separately for body text, informative lines/markers, selections, and diagram callouts, including text over images. Distinguish key categories by text, shape, line pattern, or position as well as color. A thin line may remain unsuitable for projection even when its measured contrast is adequate.
- For relevant distributed, teaching, or reading decks, retain meaningful slide titles, set reading order by argument, give informative visuals concise alt text, and mark decorative objects as decorative. Avoid repeating nearby readable text in alt text or narrating every decorative arrow.
- Plan necessary native groups and reading order before animation. Grouping animated objects can discard effects; reordering can change overlap. During a requested review, inspect the affected visual result or playback after such a change. Do not regroup an already validated sequence merely to clear a checker warning.
- Only for a requested accessibility review, run the available application checker, then inspect material gaps. Its coverage varies by application/version; record the environment when making a check claim. Do not promise that it covers all graphic objects or that it always misses transparent backgrounds.
- WCAG contrast ratios can inform a deck check: 4.5:1 for ordinary text, 3:1 for large text under the standard's size definition, and 3:1 for necessary non-text graphics with its stated exceptions. These are web criteria, not certification of the entire PPT; evaluate actual Chinese glyph size and viewing conditions too.

References: [Microsoft accessible presentations](https://support.microsoft.com/en-us/accessibility/powerpoint/make-your-powerpoint-presentations-accessible-to-people-with-disabilities), [reading order and grouping warning](https://support.microsoft.com/en-us/powerpoint/make-slides-easier-to-read-by-using-the-reading-order-pane), [W3C text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum), and [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast). Microsoft's [2026-04-02 update](https://techcommunity.microsoft.com/blog/microsoft365insiderblog/better-contrast-checking-for-slides-in-powerpoint/4504713) describes a staged rollout of transparency-aware text checking and remaining table/native-chart limitations. Check the target version and actual feature availability instead of treating that announcement as proof of local capability.

## Progressive explanation and animation

- For a new or wholly remade live-talk deck, implement meaningful native object animation on every slide, including covers, section transitions, simple conclusions, and closing slides. A simple slide may use one coordinated entrance or emphasis; complex explanations use the stages they need. Static, print, or standalone-reading requests follow their intended use. Local revisions preserve unrelated effects and do not trigger deck-wide animation additions; newly added pages follow their own intended use. Choose stages from the explanation, without imposing a click quota or making every object move.
- On content slides, animate the relevant explanation or visual target with its associated cue/text. Animating only a decorative element or the title does not implement the content's build. A cover or section slide can use a restrained title/main-visual entrance. Generic slide transitions may accompany these effects but do not count as the within-slide action.
- Decide what is visible on entry, what each click reveals or emphasizes, and what remains visible afterward. Group a diagram part, its connector, and its explanation by meaning. Do not mechanically split every slide into "all pictures first, all text second", by left/right position, or into one click per text box.
- For a method chain, normally reveal one downstream method together with its incoming arrow and relevant explanation on the same click, using coordinated effects when a native group is unsuitable. Keep preceding steps visible and show the source before its dependent step; an arrow should not point into an unexplained empty area. Do not reveal the whole chain on entry when the user requests a step-by-step build. See the [cumulative method-chain example](research-explanation.md#cumulative-method-chain).
- For a live explanation of a dense plot, multi-panel figure, complex screenshot, or overall technical drawing, normally start with the overview and its essential identity, axes, units, and labels. Keep that overview stable while each relevant region cue and its associated explanation appear or receive emphasis on the same click. Choose an arrow, box, interval band, bracket, direct label, or linked enlargement by the target's geometry; do not default to arrows for every observation. See [locating evidence during explanation](research-explanation.md#locating-evidence-during-explanation).
- Plan each key observation together with its evidence target, cue, click stage, and retained context in the existing story plan or notes when needed. Keep earlier evidence available for comparisons; fade or remove obsolete cues when their accumulation obscures the figure. Preserve record/panel identity and time or spatial correspondence between the overview and any enlargement. Use the [overview and local-waveform examples](worked-examples.md#overview-with-progressive-annotations); adapt their stages to the actual evidence rather than imposing a click quota. Show dependencies before their consequences.
- Choose effects from the relationship being explained: progressive reveal for dependencies, directed movement for flow, movement about equilibrium for vibration, linked enlargement for detail, and aligned state switching for comparisons. Use Appear/Fade for labels and simple builds; mechanism pages may need the object itself to move or change. Follow [effect selection and implementation](implementation-and-checks.md#choose-the-effect-from-the-explanation).
- Keep the speaker in control: a click can start a short coordinated sequence, followed by a stable reading state. Use direction and timing that make the change understandable. Around 0.3-0.5 seconds is a starting point for a simple fade, not a rule for mechanism motion. Avoid gratuitous movement, letter-by-letter text, and automatic slide advance that forces the speaker's pace.
- Determine necessary native groups and reading order before adding animation. Regrouping animated objects can discard effects, and reading-order changes can alter overlapping objects; preserve and confirm affected targets and sequencing during production. Semantic stages need not require a native group if coordinated effects preserve the intended meaning.
- Write actual native effects into the delivered `.pptx`. Speaker-note instructions alone do not implement animation. Use object effects for within-page builds; Morph may connect meaningful states across already planned adjacent pages, within the agreed count. A generic page transition alone does not implement an object build. For complex sequences, record object role/name, effect, trigger, order, duration, and entry/final visibility compactly in the existing plan. Reuse suitable effects and tools; do not assume a later export preserves them. Use [native implementation guidance](implementation-and-checks.md#native-animation) when needed.
- Keep an action for each page being created or remade in the existing plan; one sentence is enough for a simple entrance. For local revisions, update only the affected plan entries and effects. Apply [minimum production confirmation](#minimum-production-confirmation) to the actual saved targets and stages before delivery.
- If the active environment cannot implement the requested animation, state the specific limitation and continue independent work. If the request permits a static fallback and its page count, use cumulative step pages that retain earlier content, and describe the fallback explicitly. Otherwise preserve the agreed slide count and identify the unsupported feature. A lack of preview alone does not prevent delivery when the user is handling review. Do not silently deliver static slides as animated, substitute video for an editable deck, or duplicate pages to change the agreed count. For local edits, preserve unrelated effects and their object targets.

## Native animation

- Use stable object identity and semantic roles for effect targets. For a complex build, the existing plan can record `role/name -> effect -> trigger -> order -> duration/delay -> entry/final visibility`. Simple stages need no separate schema or manifest.
- When Windows PowerPoint automation is the available authorized route, `TimeLine.MainSequence.AddEffect` is one native API. Set the intended click/with-previous/after-previous behavior deliberately. Inspect both main and interactive sequences when relevant; preserve unrelated effects during local changes.

### Choose the effect from the explanation

| Meaning to convey | Suitable implementation | Construction detail |
| --- | --- | --- |
| A cover, section transition, or closing page introduces its subject | A restrained coordinated entrance of title and main visual, or emphasis on the concluding content. | Keep the complete subject readable at the end. These pages are included in the live-talk default. |
| A photograph, concept, or short explanation directs attention | Native cue and matching sentence reveal/emphasize together; use one semantic group when further splitting adds little. | Animate the actual subject of the page. Do not fragment a sentence into letter-by-letter or word-by-word effects. |
| A component, dependency, or observation becomes relevant | Native Appear/Fade, coordinated with the associated arrow, cue, and text. | Keep the earlier dependency visible. Name the targets by role before assigning effects. |
| Flow along a path | Directional Wipe on a native connector, optionally followed by a marker's native motion path. | Match the actual path/direction and show the destination before a marker reaches it. The marker represents flow, not a measured transit time unless a source supplies that timing. |
| Vibration or another recurring mechanism | Native motion paths or rotation about an explicit reference, with a short coordinated sequence. | Keep an equilibrium mark or other fixed reference. Return to a stable state; do not substitute label fades for the motion being taught. |
| Overall object and selected detail | Native enlargement plus emphasis on the source region; Morph between suitable already planned adjacent slides. | Preserve overview/detail correspondence and readable context. Keep identifiers attached to the same source. |
| Two measured states or before/after data | Aligned source charts/panels with coordinated reveals or state switching. | Keep axes and units fixed where comparison requires it. Display actual endpoints; do not invent interpolated observations. |
| A designed structural or spatial change | Native position/size/rotation effects within a page, or Morph across meaningful planned pages. | Keep object identity consistent and make the starting and ending geometry explainable. Respect the agreed slide count. |

Set effect targets, start/end positions or path, trigger, order, duration, repeat behavior, and retained visibility through the active author's supported animation API. A click may start several coordinated effects using with-previous/after-previous timing; leave the next substantive stage under presenter control. Derive timing from the visible action, not one fixed duration for all effects. The [mechanism](worked-examples.md#mechanism-motion-with-editable-objects) and [scene-and-flow](worked-examples.md#monitoring-scene-and-acquisition-flow) examples define concrete target roles and click sequences.

For Morph, use shared object identity across the two planned pages. Where explicit matching is needed, the documented naming scheme uses the same unique name beginning with `!!` on the corresponding objects. Set actual different position/size/rotation states and the native transition; a note saying “Morph” is insufficient. Charts do not geometrically morph; use real chart states or panels for data comparisons. See [Microsoft Morph guidance](https://support.microsoft.com/en-us/powerpoint/morph-transition-tips-and-tricks).

For a dense continuous scientific mechanism, a deterministic renderer such as [Manim](https://github.com/ManimCommunity/manim) is an optional route when a media illustration fits the agreed deliverable. Use defined equations/parameters, retain the source, embed the rendered clip in the deck, and keep accompanying text, annotations, and required relationships native. A video layer does not make its internal particles/curves editable in PowerPoint. Prefer native effects when they meet the requirement, and do not silently substitute a clip for required editable motion or install another framework merely to add routine animation.

### Requested animation review

- For a requested animation review, inspect targets, order, triggers, duration, delay, entry/exit behavior, and intermediate legibility in the saved deck, then play the relevant sequences in the agreed application. Keep the deck unchanged when the request is review-only. If an authorized repair requires re-export, repeat the affected requested checks; static rendering or timing XML cannot replace playback evidence.
- Rehearse only when requested. During rehearsal, keep the speaker in control unless automatic advance is requested. [Rehearse Timings](https://support.microsoft.com/en-us/powerpoint/training/rehearse-and-time-the-delivery-of-a-presentation) can record timing; check manual advance afterward when needed. Distinguish planned duration, an automated playback check, and actual spoken rehearsal.

References: [Microsoft AddEffect](https://learn.microsoft.com/en-us/office/vba/api/powerpoint.sequence.addeffect), [BrightCarbon on pacing](https://www.brightcarbon.com/blog/how-to-be-a-powerpoint-animation-ninja-in-7-easy-steps/), and [PowerPointLabs AnimateInSlide](https://github.com/PowerPointLabs/PowerPointLabs/blob/79e6be4882b736a0cb4828e06a96286de9b3aed6/PowerPointLabs/PowerPointLabs/AnimationLab/AnimateInSlide.cs). The latter includes deletion of existing effects on selected objects; do not copy that behavior into a preservation-focused local edit. Its [test comparison helper](https://github.com/PowerPointLabs/PowerPointLabs/blob/79e6be4882b736a0cb4828e06a96286de9b3aed6/PowerPointLabs/Test/Util/SlideUtil.cs) illustrates separate content/image/animation checks, but does not compare every animation property. Actual playback is required for a claim that playback was checked, not for ordinary direct delivery.

## Portable delivery and scoped regression

- When native editing/portable delivery checks are requested, inspect the saved authoritative deck. For requested edit trials, use a temporary copy and keep the authoritative file unchanged unless repair is authorized. Check embedded chart data, image/media links, and offline dependencies as applicable. Test only the agreed applications and environments; do not build a default cross-platform matrix. Remove the disposable test copy after the check rather than delivering it as another final deck.
- During a requested regression review, compare affected content and relevant dependencies against the pre-edit baseline. Inspect untouched pages/effects proportionately when the tool rewrites shared resources or whole packages. A changed file hash is not a slide-level regression, and identical images do not certify unchanged animation.
- Report demonstrated review findings with evidence. When repair is also authorized, fix the relevant problem and repeat only affected requested checks. Reuse existing QA notes; add no alternate deck, PDF, or report unless it serves the requested delivery. State remaining font/media dependencies or unavailable checks precisely.

## Delivery and optional review

Deliver the complete requested presentation and any agreed source files. Briefly state the result and its location. When animation was written but not played, describe it as implemented, without claiming playback validation. Do not list every review step the user chose to perform personally or imply that direct delivery is an incomplete task.

For a review-only request, deliver findings, their location/evidence, and suggestions without saving changes to the deck. For review with repair, identify the implemented corrections and any remaining issue after the affected requested checks. Keep content/source inspection, static rendering, native-object/data inspection, playback, and rehearsal distinct, and stop when the requested scope is satisfied. See the [task-boundary cases](worked-examples.md#task-boundary-cases) for scoped review, local edits, and direct delivery.
